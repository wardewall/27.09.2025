# Отчёт по тестовому заданию: сервис фоновой загрузки файлов (27.09.2025)

Краткий отчёт о том, что реализовано, как это соответствует требованиям, и как запустить/проверить сервис.

## Соответствие требованиям

- Приём задач со списком ссылок: реализован endpoint `POST /tasks`, который принимает массив URL.
- Скачивание файлов в папку: файлы сохраняются в `data/downloads/{taskID}`; имя файла берётся из URL (с санитизацией).
- Получение статуса задачи: доступны `GET /tasks` и `GET /tasks/{id}` с детальной информацией по каждому файлу (прогресс, ошибки).
- Устойчивость к рестарту/остановке: задачи и прогресс сохраняются в файловом хранилище (JSON). При старте незавершённые задачи переводятся в `pending` и автоматически дозапускаются. Во время graceful shutdown HTTP остаётся доступен до финала, новые задачи можно отправлять; они сохраняются и будут обработаны после рестарта.
- Внешняя инфраструктура не используется: только стандартная библиотека Go и файловая система (без Docker/БД/Nginx).
- Практики/паттерны: описаны ниже (атомарная запись, разделение слоёв, очереди и воркеры, таймауты, ретраи, graceful shutdown).

## Архитектура (высокоуровнево)

- `internal/storage` — файловое хранилище задач (JSON на диск):
  - атомарная запись через временный файл и `rename`;
  - при старте чтение всех задач; `running` - `pending` для восстановления;
  - in-memory кэш для быстрых операций + синхронизация на диск.
- `internal/service` — менеджер и воркеры загрузки:
  - очередь задач, конкурентные воркеры, `http.Client` с таймаутом;
  - ретраи задач (по умолчанию 2) при частичных сбоях;
  - прогресс каждого файла: `bytesTotal`, `bytesDone`, отметки времени.
- `internal/api` — HTTP поверхность на `net/http`:
  - `POST /tasks`, `GET /tasks`, `GET /tasks/{id}`;
  - простая маршрутизация на `http.ServeMux`, базовый логгинг запросов.
- `cmd/main.go` — композиция и жизненный цикл:
  - конфиг через переменные окружения; старт менеджера и HTTP;
  - корректная остановка: сначала воркеры (через контекст), затем HTTP.

## HTTP API

- `POST /tasks`
  - Тело запроса: `{ "urls": ["https://example.com/a", "https://.../b"] }`
  - Ответ: `202 Accepted` и JSON-задача

- `GET /tasks`
  - Ответ: список всех сохранённых задач

- `GET /tasks/{id}`
  - Ответ: подробности по задаче, статусы по каждому файлу

Примеры:

```bash
curl -X POST http://localhost:9091/tasks \
  -H "Content-Type: application/json" \
  -d '{"urls":["https://example.com/file1.zip","https://example.com/file2.jpg"]}'

curl http://localhost:9091/tasks

curl http://localhost:9091/tasks/{id}
```

## Сборка и запуск

```bash
go run ./cmd
```

Переменные окружения:

- `APP_DATA_DIR` — директория данных (по умолчанию `./data`)
- `APP_HTTP_ADDR` — адрес HTTP-сервера (по умолчанию `:9091`)

## Поведение при остановке/перезапуске

- При остановке сначала завершаются воркеры (через отмену контекста), затем c небольшим таймаутом останавливается HTTP.
- Во время остановки HTTP остаётся доступен, новые задачи сохраняются и дождутся обработки после рестарта.
- При старте все задачи перечитываются; те, что были в `running`, переводятся в `pending` и ставятся в очередь заново.

## Структура проекта

- `cmd/` — точка входа (конфиг, запуск, graceful shutdown)
- `internal/api/` — HTTP API
- `internal/service/` — менеджер и воркеры
- `internal/storage/` — типы и файловое хранилище задач
